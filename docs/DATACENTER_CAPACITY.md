# ظرفیت‌سنجی اولیه دیتاسنتر هندبوک توزیع

این سند ظرفیت‌سنجی اولیه است، نه تضمین تعداد درخواست یا زمان پاسخ. تعداد ۱۰٬۰۰۰ کاربر ثبت‌شده به‌تنهایی concurrency را مشخص نمی‌کند؛ ظرفیت نهایی باید با الگوی واقعی جستجو، اندازه فایل‌ها، تعداد صفحات، OCR و آزمون بار تعیین شود.

## تفکیک سرویس‌ها

| سرویس | استقرار پیشنهادی Production | ملاحظات |
|---|---|---|
| API | حداقل ۲ نمونه، هرکدام ۴ vCPU و ۸ GB RAM برای شروع | بدون فایل‌های حجیم در حافظه؛ پشت Load Balancer |
| PostgreSQL | ۴ تا ۸ vCPU، ۱۶ تا ۳۲ GB RAM، SSD/NVMe | Primary + replica، backup و PITR |
| OpenSearch | ۳ data node، هرکدام ۴ تا ۸ vCPU و ۱۶ تا ۳۲ GB RAM | heap حدود نصف RAM؛ snapshot مستقل |
| Redis | سرویس HA مستقل | فقط cache و داده‌های کوتاه‌عمر؛ منبع حقیقت نیست |
| Object Storage | ظرفیت اولیه حداقل ۱۰۰ GB قابل توسعه | نسخه‌برداری، checksum و lifecycle |
| Index Workers | ۲ تا ۴ worker قابل افزایش | OCR جدا از پاسخ فوری Search API |
| OCR Workers | حداقل ۲ worker قابل افزایش | محدودیت concurrency برای جلوگیری از فشار CPU/RAM |

## برآورد ذخیره‌سازی

- ۲۰ GB فایل اصلی، حداقل ظرفیت خام اولیه نیست؛ فضای رشد و نسخه‌های پشتیبان نیز باید لحاظ شود.
- برای شروع، ۱۰۰ GB فضای Object Storage قابل توسعه در نظر گرفته شود؛ میزان واقعی با تعداد نسخه‌ها و فایل‌های جدید تغییر می‌کند.
- اندازهٔ OpenSearch به متن استخراج‌شده، تعداد chunkها، analyzer و replica وابسته است و از روی حجم PDF خام قابل محاسبهٔ دقیق نیست.
- پس از ورود نمونهٔ واقعی اسناد، نسبت حجم ایندکس به فایل اصلی اندازه‌گیری و ظرفیت نهایی تعیین شود.
- Snapshotهای OpenSearch و backup دیتابیس نباید فقط روی همان دیسک میزبان اصلی نگهداری شوند.

## آزمون بار پیش از انتشار

آزمون‌ها باید با مجموعه‌ای از اسناد واقعی و مجاز، نه دادهٔ ساختگی کوچک، انجام شوند. اسکریپت پایهٔ k6 در `backend/tests/load/search.js` قرار دارد و با `API_BASE_URL` و در صورت نیاز `ACCESS_TOKEN` اجرا می‌شود:

1. ۱۰۰، ۲۵۰ و ۵۰۰ کاربر هم‌زمان برای Search API.
2. جستجوی فارسی دقیق، عبارت، غلط املایی، فیلتر زبان و صفحه‌بندی Cursor.
3. هم‌زمانی بارگذاری فایل، OCR و reindex با جستجوی عادی.
4. قطع موقت OpenSearch، Redis، PostgreSQL و Storage و بررسی رفتار بازیابی.
5. اندازه‌گیری p50/p95/p99، نرخ خطا، CPU، RAM، disk IOPS، heap و صف Worker.
6. آزمون بازیابی backup دیتابیس و Object Storage.

## اهداف اولیهٔ قابل سنجش

- هدف اولیهٔ Search API در بار عادی: p95 کمتر از ۱٫۵ ثانیه؛ این هدف باید با آزمون واقعی تأیید شود.
- OCR و indexing هیچ‌گاه در مسیر پاسخ Search API اجرا نمی‌شوند.
- فایل اصلی فقط با درخواست کاربر و لینک کوتاه‌عمر دریافت می‌شود.
- هیچ ایندکس ۲۰ GB روی گوشی دانلود نمی‌شود.
- SQLite و صف Outbox منبع حفظ داده‌های محلی هستند؛ Redis و cache قابل حذف و بازسازی‌اند.

## توسعهٔ ظرفیت

افزایش API و Worker به‌صورت افقی انجام می‌شود. OpenSearch پس از اندازه‌گیری shard size و query profile گسترش می‌یابد؛ تعداد shard و replica نباید بدون benchmark ثابت شود. PostgreSQL با connection pooling، ایندکس‌گذاری queryهای واقعی و replica خواندنی بهینه می‌شود. هیچ عدد ظرفیت نهایی قبل از آزمون بار و مشاهدهٔ دیتاست واقعی تأیید نمی‌شود.
